Core features

01
질문 카드 → AI 추천 파라미터
사용자 여행 스타일·선호도·체력 정보를 질문 카드 형식으로 수집하여 AI 추천 파라미터로 변환.
02
Gemini × Kakao Mobility 루트 시각화
Gemini API로 여행지 루트 자동 생성 + Kakao Mobility API로 이동 경로 시각화. OpenWeather 연동으로 날씨 조건 반영한 일정 최적화.
03
외부 API 추상화 레이어
기상청 API 응답 불안정 문제 — 추상화 레이어 설계 후 OpenWeather로 교체. 외부 API 의존성 관리의 중요성을 실전으로 학습.
04
방어적 JSON 파싱 Fallback
Gemini 응답의 키 순서/누락 불규칙 문제 — JSON 구조 패턴 분석 후 기본값 처리 Fallback 추가. 이 경험이 TrendLens의 구분자 기반 Fallback 전략으로 발전.
05
Spring Security 기반 인가 체계
로그인/인가 체계 및 회원별 여행 기록 관리. JSP PoC의 세션 기반 인증을 Spring Security로 안정적으로 이식.
06
Health Care 부가 기능
이동 거리·시간·체중 기반 칼로리 자동 산출, 관리자 전용 공지사항 CRUD + 등급 기반 접근 제어 등 부가 도메인까지 구현.

Troubleshooting — 3 cases

01 · 기상청 API 교체 — 추상화 레이어 설계
문제기상청 공공 API 연동 시 응답 포맷 불안정 및 간헐적 타임아웃으로 서비스 안정성 저하
해결API 추상화 레이어 설계 후 OpenWeather로 교체 — 이후 다른 날씨 API 교체도 용이한 구조
결과날씨 연동 기능 안정화, 외부 API 의존성 관리의 중요성 체감
02 · Gemini API JSON 응답 불규칙 문제
문제AI 응답이 매 요청마다 키 순서 변경, 일부 필드 누락 등 포맷이 일정하지 않아 파싱 오류 발생
해결JSON 구조 패턴 분석 후 방어적 파싱 로직 구현, 필드 누락 시 기본값 처리 Fallback 추가
결과파싱 성공률 크게 향상 — 이 경험이 TrendLens의 구분자 기반 Fallback 전략으로 발전
03 · AI 환각 & 좌표 어긋남 — Kakao Local 검증
문제Gemini가 생성한 장소 일부가 실제 존재하지 않거나, 좌표가 요청 도시와 다른 지역으로 어긋남. 초기 구현에서는 이 검증 로직 자체가 부산 bounding box + "주소에 부산 포함" 체크로 하드코딩돼 있어, 부산 외 도시를 요청하면 검증이 아예 통과 불가능하거나 동명이인 장소로 잘못 확정되는 문제가 있었음.
원인LLM의 위치 정보 환각(hallucination) — 좌표 정확도를 보장하지 않음. 재검증 로직 자체도 특정 도시로 고정 개발된 상태였음.
해결Gemini 후보를 Kakao Local Search로 재검증(주소/위경도 재획득), 매칭 실패 시 stop 제거 + 인근 카테고리 대체. 지역 필터를 요청받은 도시명 기준 동적 검증으로 일반화(verifyAndCorrect(stops, city)).
결과부산·서울 실제 요청 → 각각 8/8, 9/9 스탑 전부 해당 도시 경계 좌표로 저장 확인. 서울 실존 장소 5종 재현 테스트 — 구버전 0/5 매칭(1건은 동명이인 오매칭), 신버전 5/5 정확 매칭. 4개 도시 65개 스탑 종합 실측 — 검증 없었다면 84.6%가 부정확한 위치(9.2%는 실존하지 않는 장소)였을 것을 카카오 재검증으로 100% 실존·정합 좌표만 노출.
